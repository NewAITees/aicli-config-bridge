# Spec Common Spec

## Goal

実装前に、手順ではなく要件を定義する。
AI がコードを書く前に、何を満たせば完了か、どの前提を確認すべきか、どこまでが今回の対象かを明確にする。

## Use This Skill To

- 曖昧な依頼を、実装可能な Spec に整理する
- 実装手順ではなく、達成すべき状態を定義する
- 完了基準を先に明確化する
- AI が空気読みで補完してはいけない前提条件を確認する
- スコープ、制約、対象外を切り分ける

## Core Principle

Spec は手順書ではない。
Spec の役割は、AI が何を達成すべきかと、何をしてはいけないかを判断できる状態を作ることにある。

Spec では次を優先する。

- 背景
- 目的
- 必須要件
- 成功条件
- 失敗条件
- エスカレーション条件
- 許容される判断
- 非機能要件
- 制約
- 対象外
- 受け入れ条件
- 完了基準
- 前提条件

Plan や実装方法は、Spec が固まったあとにコードベース調査を踏まえて決める。

## Shared Workflow

1. 未完了の `spec:` 項目があれば先に確認する
2. 依頼の背景と目的を確認する
3. 「これができたら正解」と言える完了基準を確認する
4. 外部から観測できる必須要件を確認する
5. 成功条件、失敗条件、エスカレーション条件を確認する
6. 必要に応じて非機能要件、制約、対象外を確認する
7. AI が暗黙に補完してはいけない前提条件を確認する
8. AI が自律的に決めてよい範囲を確認する
9. 高リスク領域かどうかを確認し、必要なら手順自体を制約として扱う
10. 理解した内容を Spec として短く構造化して要約する
11. 承認を得てから Plan と実装に進む

## Interview Rules

- まず実装方法ではなく、達成すべき結果を聞く
- 質問は「何を作るか」「何を満たせば終わりか」を明らかにするために使う
- 実装手順、使用技術、ファイル構成は、それ自体が制約でない限り先に固定しない
- ユーザーが省略した前提を、AI が空気読みで埋めない
- 「そんなこともわからないのかよ」と言われやすい箇所ほど、前提条件として明示確認する
- 複数解釈がある場合は黙って選ばない
- 不要に質問を増やさず、完了判定に必要な確認を優先する
- 成功だけでなく、失敗と停止条件も確認する
- どこまで AI が自律判断してよいかを曖昧にしない

## What To Clarify

### Background

- 現在どのような状況か
- 何が問題になっているか

### Purpose

- 誰が何をできるようになるべきか
- なぜこの変更が必要か

### Completion Criteria

- 何が満たされたら今回の作業を正解とみなすか
- 何を確認できれば完了と言えるか

### Required Behaviors

- 外部から観測できる必要な動作は何か
- 優先度の高い要件は何か

### Success Conditions

- 何をもって成功とするか
- AI が自分で完了を判断できる評価可能な条件は何か
- 数字、時間、件数、割合、閾値で表せる条件はあるか

### Failure Conditions

- 発生してはいけない状態は何か
- 完了扱いにしてはいけない状態は何か
- 即停止すべき失敗と、修正して継続できる失敗は何か

### Escalation Conditions

- どの条件で人間確認が必要か
- 誰に確認すべきか
- どの程度の不確実性まで自律判断してよいか
- 確信度の閾値を置くべきか

### Allowed Autonomy

- AI が既存規約に従って自律判断してよい実装詳細は何か
- 前提条件が確定している範囲で委ねてよい判断は何か

### Non-Functional Requirements

- 性能
- 安全性
- 保守性
- 互換性
- アクセシビリティ
- 可観測性

### Constraints

- 変更してはいけない部分
- 必須技術や既存方針
- 追加禁止の依存関係
- セキュリティ上の境界

### Out Of Scope

- 今回やらないこと
- 別タスクに分けること

### Preconditions

- 依頼が成立するために共有されているべき前提は何か
- 用語の意味、対象読者、運用条件、既存ルールに解釈差がないか
- 前提条件が未確定のままでは、自律判断してはいけない論点は何か

## What Not To Do

- 実装手順をそのまま Spec として扱わない
- 曖昧な表現を、AI の推測だけで具体化しない
- 完了基準がないまま実装に進まない
- 前提条件が不明なまま「たぶんこうだろう」で進めない
- スコープを勝手に広げない
- 高リスクでない領域まで不要にプロセス固定しない
- 成功条件と受け入れ条件を混同しない
- 軽微な実装判断まで毎回エスカレーションしない

## When Process Constraints Belong In Spec

次のような場合は、手順自体が要件になりうる。

- 決済
- 認証
- 権限変更
- 本番データ削除
- 個人情報処理
- セキュリティ変更
- データ移行
- バックアップ / 復元
- 監査証跡が必要な変更

この場合は、順序や確認手順を制約として明示してよい。

## Distinctions

### Success Conditions vs Acceptance Checks

- 成功条件は、AI が「完了と言えるか」を判断する上位基準
- 受け入れ条件は、個別要件を検証する具体的な確認項目

### Completion Criteria vs Definition of Done

- 完了基準は、その依頼が正解と言える状態
- Definition of Done は、実装作業全体を完了扱いにするための共通条件

## Judgment Stop Conditions

次のいずれかに該当する場合、AI は完了扱いにせず、推測で補完せず、未確定点を明示して確認を求める。

- 成功条件を評価できない
- 前提条件が未確定である
- 失敗条件への該当有無を判断できない
- エスカレーション条件に該当する可能性を否定できない
- Definition of Done の達成状況を検証できない

## Output Quality Bar

- 実装方法ではなく要件として読めること
- 完了判定に使えること
- 曖昧な前提が残っている場合は、その未確定点が明示されていること
- Spec / Plan / Code が混ざっていないこと
- 成功、失敗、停止、引き継ぎの境界が読めること

## Guardrails

- Goal ではなく要件を固める意識で進める
- 完了基準を確認する前に実装へ進まない
- AI は空気を読まない前提で、必要な前提条件を確認する
- 複数解釈がある場合は黙って選ばない
- 高リスク領域ではプロセス制約を省略しない
- 前提条件が未確定な論点では自律判断しない
- 成功条件、失敗条件、エスカレーション条件を区別して扱う
