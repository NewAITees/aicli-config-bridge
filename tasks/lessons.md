## meta — AIとの協働ルール
### 調査: ls -R は dotfile を表示しないため「ディレクトリが空」と誤認する
- **症状**: `project-configs/` を空と判定し「設計図のソースが全て存在しない」と誤った分析を報告した
- **原因**: `ls -R` はドットで始まるファイル・ディレクトリを表示しない（`.claude/` が見えなかった）
- **対策**: ディレクトリの存在確認は `ls -la` を使う。さらにツール自身の `status` コマンドのような実行可能な検証手段があれば、目視より先にそれを実行する

### 調査: 設定ファイル探索ではシンボリックリンクの実体も確認する
- **症状**: リポジトリ直下の `.codex/` だけを検索し、`symbolicLink/.codex` の実体にある `AGENTS.md` を見落とした
- **原因**: 通常ファイルの一覧だけで不存在と判断し、設定配置先を示すシンボリックリンクを辿らなかった
- **対策**: 管理対象設定を探すときは `ls -la` と `readlink -f` でリンク先を確認し、必要に応じて実体側も検索する

## boundary — データ型・変換・境界契約

### hooks: 互換イベント名でも出力契約の差を正規化する
- **症状**: RTKのClaude用Hookは`updatedInput`を返すが、Codexが必須とする`permissionDecision: allow`を返さない
- **原因**: 両Agentが`PreToolUse`を採用していても、書き換え許可を表すJSON契約が完全には同じでない
- **対策**: 共通処理は正本として再利用し、Agent固有の薄いアダプターで不足フィールドだけを補う。実入力で書き換えと二重適用防止を検証する

### hooks: OS固有コマンドはcommandとcommandWindowsで分離する
- **症状**: WSL用の`/usr/bin/python3`と`/home/...`を使うHookはWindowsネイティブCodexで実行できない
- **原因**: Hookの意味は共通でも、ランタイムとファイルパスがOS境界を越えられない
- **対策**: 共通の`hooks.json`で`command`と`commandWindows`を明示し、OS別の薄いアダプターを同じ出力契約のテストで固定する

## architecture — 設計・責務・config
### docs: ドキュメントは実装に従属させ、未実装機能を「ある」と書かない
- **症状**: CLAUDE.md/README が旧アーキテクチャ（config/, linker/, tools/）と未実装機能（Windowsコピー運用）を説明し続け、新規ユーザーとAIが必ず失敗する状態だった
- **原因**: 実装を大きく作り直した際（phase1/phase2）にドキュメントと旧開発計画（USAGE.md）を同期・削除しなかった
- **対策**: 実装変更と同じコミットでドキュメントを更新する。将来計画は要件定義ファイル（docs/REQUIREMENTS_SYNC.md 等）に分離し、現状説明と混ぜない

### skills: 共通仕様を正本にして各エージェントは薄いアダプタにする
- **症状**: codex と claude で同名機能の説明粒度や有無がずれ、片方にしか運用知識が残る
- **原因**: スキル本文を各環境で独立運用し、共通仕様と環境差分を分離していない
- **対策**: 共通仕様をリポジトリ内ドキュメントに置き、各 `SKILL.md` は環境固有メモだけを持つ

### skills: spec は手順書ではなく完了基準と前提条件を定義する
- **症状**: spec が「要件を軽く聞くだけ」の薄い入口になり、実装前に何が正解かと前提条件が固まらない
- **原因**: Goal や Scope の確認に寄りすぎ、Completion criteria と Preconditions を明示的に扱っていない
- **対策**: spec では背景、目的、完了基準、前提条件、制約、対象外を優先して整理し、Plan や実装手順を先に固定しない

### skills: spec は成功だけでなく失敗と停止条件も定義する
- **症状**: 成功条件だけでは、AI が「いつ止まるべきか」「何を未完了扱いにすべきか」を安定して判断できない
- **原因**: Failure conditions、Escalation conditions、Definition of Done、Judgment stop conditions の区別が弱い
- **対策**: spec では成功条件、失敗条件、エスカレーション条件、許容される判断、停止条件を分けて定義する

### security: パッケージファイアウォールの対応範囲を導入前に確認する
- **症状**: Socket Firewall FreeでAPTを包み、未対応のUbuntuリポジトリ通信が405で失敗した
- **原因**: `sfw`をすべてのパッケージマネージャーに適用できると誤認した
- **対策**: `sfw`の正式対応範囲を先に確認する。非対応のAPTは公式署名済みリポジトリと固定版を使い、対応するCargo依存取得は`sfw`と`--locked`で保護する

### config: ホーム側だけの設定はシンボリックリンクでも別PCへ移植されない
- **症状**: `~/.codex/AGENTS.md` は存在しても、実体がGit管理外のWindowsホームにあり、cloneした別PCへ内容が移らない
- **原因**: 配置先へのリンクはあったが、リポジトリ内に持ち運べる正本とリンク設計図の項目がなかった
- **対策**: 完成版を `project-configs/` に正本化し、WSL・Windows両方の配置先を `aicli-links.json` で管理する

### skills: Agentのskillsディレクトリ全体を置き換えない
- **症状**: skills全体を共有リンクにすると、Codexの`.system`やプラグイン領域、Agent固有スキルまで巻き込む
- **原因**: 共有したい自作スキルと、ツールが管理するスキルの所有境界を分けていない
- **対策**: Git正本をshared/codex/claudeへ分け、個々のスキルだけを配置する。`.system`、キャッシュ、秘密情報は除外する

## quality — テスト・CI/CD・品質保証
### CLI境界: 機械可読出力と終了コードをテストで固定する
- **症状**: `status --json` がテーブルとJSONを同時に出力し、`apply` の処理エラーも終了コードへ反映されていなかった。
- **原因**: CLI出力とドメイン処理の成功判定を個別にテストしていなかった。
- **対策**: 機械可読モードは専用出力にし、入力値検証とエラー終了をCLI境界で行う。対象外リンクを削除しない安全性もテストで固定する。
